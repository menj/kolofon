# Single source of truth

This document records where each piece of theme state is authoritative. When
two places appear to define the same thing, the file named here wins and the
other is a consumer.

## Principle

`inc/defaults.php` is the single source of truth for every default value the
theme ships with. Nothing else hard-codes a default. The options page reads it
for reset and fallback, `inc/dynamic-css.php` reads it when an option is
missing or invalid, and templates read it through `opt()`.

A fresh install and a reset install must render identically. That property
only holds while every default lives in one function.

## Hard invariants

Constraints that cannot be relaxed without a deliberate version bump and an
entry in `../guides/upgrading.md`. Each has a failure mode named so future edits
can weigh the trade honestly.

1. **`inc/defaults.php` `get_raw_defaults()` is the only place a default lives.**
   Failure mode: fresh install and reset install render differently, or an
   option renamed in one file goes stale in another.
2. **Every option key must appear in defaults, schema, and sanitiser.** Enforced
   by the parity audit run before every build. Failure mode: an option that
   can be set but never read, or read but never sanitised.
3. **`opt()` and `get_defaults()` must not memoise until `after_setup_theme`
   has fired.** The `filters_settled()` guard protects this. Failure mode:
   options filtered in through `kolofon_defaults` are silently dropped from
   sanitisation on save, because the registry was frozen too early.
4. **`protected_mailto()` owns the `class` and `rel` attributes of the anchor
   it builds and merges caller values into a single deduplicated attribute.**
   Callers pass extras through the attrs array, never by concatenating strings.
   Failure mode: HTML keeps only the first occurrence of a repeated attribute,
   silently dropping the caller's value. The email icon regression fixed in
   2.0.1 was exactly this.
5. **Removing or renaming an option key requires a major version bump AND a
   migration routine in `migrate_stored_options()`.** Failure mode: stored
   rows on upgrade fall through the sanitiser's enum fallback to the default,
   silently overwriting the user's choice.
6. **Reviving a previously-retired slug with new semantics requires a one-shot
   migration flag.** The 2.5.0 typewriter revival illustrates: without the
   `kolofon_typewriter_reset` flag, either the old meaning survives (visual
   drift for existing users) or every new selection is rewritten on the next
   load (option is un-pickable).
7. **Text domain is `kolofon`.** Every user-facing string passes through a
   gettext function with this domain, verified against the `.pot` file.
8. **Absolutely-positioned elements must have their containing block audited
   before shipping.** When a CSS design assumes a preview positions against
   `.post-list`, the DOM chain must actually deliver that: no intermediate
   ancestor may have `position: relative` unless deliberate. Failure mode: the
   2.9.4 hover preview shipped three times before catching that
   `.post-item a` had `position: relative` set for an older design, silently
   redirecting the containing block one level down and breaking the reserved
   gutter mechanic. The DOM is the source of truth, not the abstraction.
9. **The activation hook (`after_switch_theme`) must be idempotent.** The
   2.6.0 blog page auto-provisioning relies on this: on reactivation it
   checks by template (not slug) for an existing Blog Index page and does
   nothing if one is present. Failure mode: reactivating the theme would
   create a `blog-2`, `blog-3`, ... every time the user cycled themes.

## Option keys

All keys live inside the single `kolofon_options` array option. There are no
loose options in `wp_options`.

| --- | --- | --- |
| `hero_heading` | restricted inline HTML | `Mohd Elfie Nieshaem Juferi` |
| `hero_eyebrow` | text | empty |
| `hero_body` | post HTML | Bio paragraph |
| `hero_portrait` | URL | empty, falls back to `assets/img/profile.png` |
| `footer_text` | post HTML | Copyright line with current year |

### Social

One key per platform, `social_` prefix, all defaulting to empty except GitHub.
An empty value means the icon is not rendered.

`social_mastodon`, `social_x`, `social_linkedin`, `social_github`,
`social_youtube`, `social_instagram`, `social_facebook`, `social_threads`,
`social_pinterest`, `social_email`, `social_rss`

### Sections

| Key | Type | Default |
| --- | --- | --- |
| `section_slugs` | comma or newline separated slugs | empty |
| `section_all_label` | text | `All` |
| `enforce_single_section` | bool | `1` |
| `scope_adjacent_posts` | bool | `1` |
| `show_section_chooser` | bool | `1` |

Sections are mutually exclusive: a post belongs to exactly one category. Tags
carry topics that cut across sections. Enforcement runs server-side on
`save_post`, which is authoritative and covers REST, WP-CLI, Quick Edit, and
imports; `assets/js/single-section.js` makes the block editor panel agree with
the rule but is not relied upon.

When a post carries several categories the theme keeps the first configured
section in configured order, falling back to the first assigned category when
none of them is a section. The rule is deterministic, so the same input always
yields the same result.

Tags are the counterpart and are deliberately left unconstrained. A post lives
in one section and carries any number of tags, so tags are the only mechanism
for a topic that crosses sections. A tag archive is therefore the opposite of a
section archive: it gathers posts from everywhere, so the section chooser is
suppressed there and a section breakdown shown instead.

**Known coupling.** Taxonomy terms are content and survive a theme switch, but
this enforcement does not. Strictly it belongs in a companion plugin. For a
single-author site that controls its own theme the trade is accepted
deliberately rather than overlooked.

### Appearance additions

| Key | Type | Default |
| --- | --- | --- |
| `planned_badge_label` | text | `Soon` |
| `planned_notice_text` | text | sentence |

The colour system offers exactly three choices: Charcoal (the default), Ivory,
and Auto.
Auto is a pairing, not a palette: `build_root_css()` emits Ivory as the base
`:root` block, so browsers without media query support get a complete light
theme, then Charcoal inside `prefers-color-scheme: dark`, then
`color-scheme: light dark`. Both palettes pass WCAG AA on every declared pair,
verified computationally, so no configuration can produce a failing contrast.

`resolve_palette()` maps any unknown slug, including schemes removed in 2.0.0,
to Charcoal, so "default" means one value everywhere. `migrate_stored_options()` in `inc/hooks.php` rewrites stored rows
across breaking schema changes and records what each major removed.

Page state lives in post meta, not in the option row, so it survives a theme
switch as data and is visible to REST.

### Privacy

| Key | Type | Default |
| --- | --- | --- |
| `email_obfuscation` | enum | `js` |
| `disable_file_edit` | bool | `1` |
| `emit_meta_tags` | bool | `1` |

`emit_meta_tags` is a request rather than a guarantee. `meta_output_enabled()`
returns false whenever a known SEO plugin is active, regardless of the option,
because emitting a second set of Open Graph tags or a second JSON-LD graph is
worse than emitting none: consumers disagree about which wins. Override with
the `kolofon_seo_plugin_active` filter for a plugin the list does not know.

`disable_file_edit` is read directly from the stored option rather than through

anything. An install with no saved preference is protected by default. If
`DISALLOW_FILE_EDIT` is already defined in `wp-config.php`, that definition
wins and this option cannot loosen it.

## Breakpoints

Three content breakpoints, declared once at the foot of `assets/css/main.css`.
Do not introduce new ones; extend these.

| Width | Covers | Principal changes |
| --- | --- | --- |
| 1024px and below | Tablet landscape, small laptops | Tighter gutters, hover previews stop |
| 768px and below | Tablet portrait | Navigation collapses to a toggle, hero stacks, base size drops to 16px |
| 560px and below | Phones | Post rows stack, search form stacks, footer tightens |

Two capability queries sit alongside them and are not width-based:

- `(hover: hover) and (pointer: fine) and (min-width: 1024px)` gates the hover
  previews. The deciding factor is whether a hover state exists at all, not
  screen width alone, so a width query on its own would be wrong.
- `(pointer: coarse)` raises hit areas to 44px, the figure both Apple's
  guidance and WCAG 2.2 settle on.

The admin options page uses a single breakpoint at 782px, matching where
WordPress collapses its own admin chrome.

### The caching rule, and why it exists

`opt()` and `get_defaults()` memoise, but **only once `after_setup_theme` has
fired**. Before that they recompute on every call.

This is not an optimisation detail. A read during theme load would otherwise
cache a view of the defaults built before child themes and plugins had
registered, making a filtered-in option permanently invisible for that request.
`filters_settled()` in `inc/hooks.php` is the guard. Do not remove it, and do
not add a memo elsewhere without the same check.

### The schema rule

Tabs and fields are declared as data in `inc/options-schema.php` and registered
by a single loop. A settings section is created for every tab automatically, so
an extension adding a tab does not need to know that a tab and a section are
separate concepts in the Settings API. Built-in and filtered-in fields go
through the same registration path, so an added field cannot behave differently
from a native one.

Where help text depends on runtime state, the declaration holds a callable
resolved at registration rather than a string, which is why the file editor and
metadata toggles can report what `wp-config.php` and the active SEO plugin are
doing.

### The sanitiser rule

`sanitize_options()` iterates the **filtered** defaults, not a literal list, and
resolves each key through the registry. That is what makes a filtered-in option
survive a save. The previous hard-coded body named every key explicitly, so an
option added by a filter was read once and then silently discarded on the next
save.

A key with no registry entry falls back to `sanitize_text_field`. A key whose
default is exactly `0` or `1` is treated as a checkbox, so absence from a POST
means off rather than fall back to default.

**Caveat when adding a checkbox through a filter.** The checkbox detection
decides whether an absent value means off; the registry decides what that value
becomes. Without a registered boolean callback an unticked box stores an empty
string rather than `0`, which is falsy but untidy and will not match a strict
comparison. Register a callback returning `0` or `1` for any boolean option you
add. Every built-in boolean already has one.

## Rules for contributors

1. Adding an option means adding it to `get_defaults()` first, then the field
   registration, then the sanitiser. Three places, always in that order.
2. Never call `get_option( 'kolofon_options' )` directly. Use `opt()`, which
   merges stored values over defaults and caches per request.
3. Never hard-code a colour or a configurable size in a stylesheet. Add a
   custom property instead.
4. Sizes are stored in px because that is how people think about type, and
   emitted in rem so they honour the reader's browser font-size setting. Do
   the conversion in `build_root_css()`, never in CSS.
5. Adding a social platform means one entry in `get_social_platforms()` and
   one matching key in `get_defaults()`. The field loop, sanitiser loop, and
   renderer pick it up with no further edits.
6. Bump `KOLOFON_VERSION` on any asset change, since it is the cache-buster.
7. `hero_heading` is the one option that permits markup, restricted to
   `mark`, `em`, `strong`, and `br` through `allowed_heading_html()`. Anywhere
   it is used as plain text, attribute, or structured data it must go through
   `wp_strip_all_tags()` first. Currently that means the portrait `alt` and the
   schema `Person` name.
8. Import runs the same `sanitize()` the form uses. Never add a second
   validation path; a value arriving from a file must be clamped and escaped
   identically to one arriving from a POST.
9. Front-end JavaScript is progressive enhancement only. Every script must
   leave a working page when it does not run. The navigation toggle is the
   worked example: the menu ships visible, and the script adds both the button
   and the class the collapsed styles key off, so the collapsed state cannot
   exist without something able to reverse it.
